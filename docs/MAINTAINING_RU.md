# Поддержка и выпуск новых версий

Репозиторий: [Ddosena/blender-final-dimensions](https://github.com/Ddosena/blender-final-dimensions). Основная ветка — **main**. Студентам отправляйте ссылку на [README](https://github.com/Ddosena/blender-final-dimensions) или [последний установочный ZIP](https://github.com/Ddosena/blender-final-dimensions/releases/latest/download/final_dimensions.zip).

Для установки студенту не нужен Git. Эти инструкции предназначены владельцу проекта и разработчикам.

## Что находится в репозитории

| Путь | Назначение |
| --- | --- |
| `final_dimensions/` | Только исходники устанавливаемого расширения. |
| `docs/` | Инструкции для студентов и снимки тестовых сцен. |
| `tests/` | Геометрические проверки и сценарии мыши в Blender. |
| `scripts/check_blender.py` | Проверка версии, расчётов, сборки, установки и при необходимости viewport. |
| `scripts/release_assets.py` | Проверка совпадения ZIP с исходниками и подготовка файлов выпуска. |
| `.github/workflows/blender.yml` | Автоматические проверки и публикация по запросу. |
| `CHANGELOG.md` | Что изменилось в каждом выпуске. |

Portable-копии Blender, рабочие `.blend`, локальные журналы и готовые ZIP не коммитятся. ZIP для студентов прикладываются к **Releases**.

## Обычный цикл изменения

1. Сделайте изменение в отдельной ветке и проверьте конкретную задачу пользователя.
2. Если изменились расчёты, добавьте численный пример. Если изменились мышь или отрисовка, проверьте их в живом Blender.
3. Для нового выпуска обновите номер **одинаково в двух местах**: `version` в `final_dimensions/blender_manifest.toml` и кортеж `bl_info["version"]` в `final_dimensions/__init__.py`.
4. Добавьте сверху `CHANGELOG.md` раздел `## 0.5.1 — YYYY-MM-DD` с новым номером и описанием. Уже опубликованный номер не используйте повторно.
5. При изменении поведения обновите инструкции. При добавлении версии Blender обновите матрицу workflow и сведения о совместимости.
6. Отправьте изменения на GitHub и создайте pull request в **main**. Проверьте результаты **Blender checks and release** перед слиянием.

## Публикация через GitHub без локальной сборки

После попадания подготовленных изменений в **main**:

1. Откройте вкладку **Actions** репозитория.
2. Слева выберите **Blender checks and release**.
3. Нажмите **Run workflow**. В **Branch** оставьте **main**.
4. Установите параметр **publish** в `true` и запустите workflow.
5. Дождитесь успешного завершения обеих задач Blender и **Publish installer**. Зелёная отметка означает успех; красная — ошибка, выпуск этой задачей не создан.
6. Откройте **Releases** и проверьте новый выпуск: версия, описание, `final_dimensions.zip`, ZIP с номером версии и `SHA256SUMS.txt`.
7. Скачайте установочный файл по постоянной ссылке и выполните контрольную установку в своей версии Blender. Публикация GitHub не устанавливает обновление в локальный Blender автоматически.

Workflow сначала проверяет геометрию, установку и реальные события мыши/GPU в двух версиях Blender. При успехе собирает файлы выпуска из проверенного commit, создаёт тег `v<версия>` и публикует Release. Файл **final_dimensions.zip** сохраняет имя, поэтому постоянная ссылка для студентов ведёт на новый выпуск. Предыдущие выпуски остаются доступными в Releases.

Не включайте **publish**, если хотите только повторить проверки. Повторная публикация уже существующего тега завершится ошибкой; увеличьте номер версии для изменённого установщика.

## Проверки и сборка на Windows

Установите Python 3.11 или новее **только для инструментов разработки**. Самому расширению отдельный Python не требуется. Скачайте нужную portable-версию Blender с [официального сервера](https://download.blender.org/release/), распакуйте её и укажите фактический путь к `blender.exe`.

Из корня проекта в PowerShell:

```powershell
$BlenderExe = '.\tools\blender-5.2.2-windows-x64\blender.exe'
python .\scripts\check_blender.py --blender $BlenderExe --gui
python .\scripts\release_assets.py
```

Проверки работают в отдельных процессах с заводскими тестовыми сценами и изолированным профилем. Они не открывают рабочую сцену и не требуют управления мышью пользователя. Не запускайте тестовые скрипты внутри своей рабочей сцены.

Без `--gui` выполняются только численные проверки, сборка, validate и установка в тестовый профиль. На Linux проверки с `--gui` требуют дисплей; CI запускает их под **Xvfb**. Численные проверки не заменяют проверку интерфейса.

Результаты появятся в `artifacts/`, установщик — в `dist/`, файлы выпуска — в `release-assets/`. Эти папки исключены из Git. Для ручной публикации после успешных проверок можно воспользоваться GitHub CLI:

```powershell
$ReleaseVersion = Get-Content .\release-assets\VERSION
gh release create "v$ReleaseVersion" .\release-assets\*.zip .\release-assets\SHA256SUMS.txt --target main --title "Final Dimensions $ReleaseVersion" --notes-file .\release-assets\RELEASE_NOTES.md --latest
```

## Поддержка новой версии Blender

1. Выберите точную опубликованную версию и проверьте ссылку на её portable-архив на официальном сервере.
2. В `.github/workflows/blender.yml` добавьте или замените пару `blender` / `series` в `matrix.include`. `series` — например `5.2`, `blender` — полный номер `5.2.2`.
3. Если заменяете сборочную версию `5.2.2`, обновите имя артефакта в задаче **release**; оно должно соответствовать новой задаче `check`.
4. Запустите проверки и контрольную установку. При ошибке API или поведения исправьте причину; не отмечайте новую версию совместимой по одному совпадению номера.
5. Обновите `TESTING.md`, README и инструкции, выпустите новый номер расширения.

Минимальную версию в manifest меняйте только при изменении фактически поддерживаемого диапазона. Не удаляйте старую LTS из проверок без причины: студенты могут продолжать ею пользоваться. Поддержка всех будущих Blender не является автоматической.
